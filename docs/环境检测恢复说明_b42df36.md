## 2. RootBeer 依赖：改为内置源码

`DetectFragment` 依赖 `com.scottyab:rootbeer`，但该构件在**所有可达的 Maven 镜像上都返回 404**（腾讯、阿里镜像均已试过），
无法作为远程依赖拉回来。RootBeer 是 Apache-2.0 开源库，因此把它的 4 个源文件直接内置进
`com.scottyab.rootbeer` 包，包名不变，`DetectFragment` 无需改调用。

`RootBeerNative` 的原生库（`libtoolChecker.so`）不在源码里，其静态块已自行 `try/catch UnsatisfiedLinkError`，
缺失时 `wasNativeLibraryLoaded()` 返回 false，相关检测自动跳过——不会崩溃，只是少了 2 项原生检查。

## 3. 还原过程中修正的三处问题

### 3.1 `HardcodedSignals` 完整性（更正此前的错误结论）

我先前判断 `b42df36` 里大部分签名 blob 是空字符串。用脚本逐个解码复核后确认：**该结论是错的**。
`b42df36` 的 36 组 blob **全部非空**，内容也比手工补出来的更完整（覆盖 crDroid / EvolutionX / PixelOS / YAAP 等 ROM 指纹、
`zygisknext` / `zygiskassistant` / `lspatch` 等关键词、完整 managerActions 等）。

因此已放弃手工补写的版本，改用上游原文件。

### 3.2 `checkDangerousBinaries()` 恒真（上游 bug）

上游实现把 `dangerousBinaries` 和 `binaryPaths` 直接拼接后逐个 `new File(x).exists()`，但这两张表的语义不同：

- `dangerousBinaries` = **文件名**：`su`、`busybox`、`magisk`、`magiskpolicy`、`resetprop`、`ksud`、`apd`…
- `binaryPaths` = **目录**：`/sbin/`、`/system/bin/`、`/system/xbin/`、`/vendor/bin/`…

结果：目录每次都命中（这一项永远报警），而真正的二进制一个都查不到（裸文件名不是路径）。
已按原意改成 **目录 × 文件名** 的叉乘匹配。

### 3.3 `Long.parseUnsignedLong` 的 API 级别

`AdvancedRuntimeDetector.checkProcessCapabilities()` 用了 `Long.parseUnsignedLong(String, int)`，
该重载是 **API 26** 才有的，而 `minSdk = 24`。在 Android 7.x 上会抛 `NoSuchMethodError`（是 `Error` 不是 `Exception`），
外层 `catch (Exception)` 兜不住，直接崩。已改为 `new BigInteger(value, 16).longValue()`，语义一致。

**基线（RootBeer，7 项）**：测试签名 · Root 管理应用 · Root 隐藏应用 · 危险应用 · SU 二进制 · Magisk · BusyBox

**深度（RootDetector，15 项）**：

| 显示名 | 检测内容 |
|---|---|
| SU 二进制 | 18 个常见 su 路径 |
| Root 相关应用 | root 包 + KernelSU 包 + 改版应用（如 ReVanced / mGoogle） |
| Magisk / KSU 路径 | magisk + kernelsu + root 路径 |
| 危险二进制 | 目录 × 文件名叉乘（见 3.2） |
| 隐藏 / 绕过模块 | 扫描模块目录名（Shamiko / TrickyStore / PIF / HMA…） |
| 可疑挂载点 | `/proc/mounts`、`/proc/1/mountinfo` 中的 root 关键字 + 路径特征 |
| 危险系统属性 | `ro.debuggable=1` / `ro.secure=0` / 解锁与校验状态 / KSU 属性 |
| 运行时注入痕迹 | `/proc/self/maps`、`/proc/1/maps`、`/proc/net/unix` |
| `/data` 上的 tmpfs | `/data/adb`、`/debug_ramdisk`、`/sbin` 上的 tmpfs |
| Root 目录近期改动 | 30 天内被改动的 root 目录 |
| LineageOS 特征 | init rc / platform jar / 权限 |
| 自定义 ROM | ROM 特征文件 + 属性 |
| Build 字段一致性 | `Build.FINGERPRINT` 与 `getprop ro.build.fingerprint` 是否一致（PIF 改属性后会露馅） |
| 高级运行时检测 | mount namespace 隔离、zygote 注入、kallsyms 可读、进程 capabilities、可疑环境变量 |
| OverlayFS 系统改写 | `/system`、`/vendor` 等受保护路径上的 overlay/tmpfs |
| 安装来源（提示性） | 非商店安装（ADB 侧载） |

## 5. 与安全页的接线

- `activity_main.xml`：在安全页容器内新增 `detectScrollView`（`NestedScrollView`）+ `layoutDetectHost`；
  容器带 `-16dp`（= `-ios_screen_edge`）左右负边距，抵消父布局内边距，让检测页 `#F5F5F5` 底色满幅铺开。
- **UI 风格说明**：`b42df36` 时期主界面已是 ios 玻璃风（`ios_glass_surface` 等），只有检测页还保留更早的紫色设计。
  因此"原本 UI"是两套——主界面沿用 ios 玻璃风，检测页按老紫色设计还原。模块下载页与设置页新增卡片均使用
  `ios_*` 配色，与主界面一致。全项目唯一新增的 UI 元素是设置页的「安全页使用摇一摇防护」开关。
- `SafetyPageController.Mode.DETECTION`（**默认**）：隐藏 Shizuku 状态卡与摇一摇防护的控件，把
  `fragment_detect.xml` 填进 host；下拉刷新 = 重新扫描；切页不会重复扫描（避免每次切页执行约 20 次 `getprop`/`cat`）。
- `Mode.SHAKE_GUARD`：设置里打开「安全页使用摇一摇防护」后切回，恢复原有 Shizuku 卡片与应用列表，并释放 Shizuku binder。
- `proguard-rules.pro`：新增 keep 规则保留 `data.detector` / `ui.detect` / `scottyab.rootbeer`，
  否则 R8 会把 `RootDetector`、`RootBeer` 竖向合并、内联掉，发布包无法与上游源码对照。

## 7. 已知局限

1. **`native-lib.cpp` 未接入**：4 个 JNI 检测（`checkForSuBinaryNative` 等）需要恢复 CMake 配置与编译产物，
   本次未做——纯 Java/Kotlin 侧已经覆盖了同样的检测面。
2. **RootBeer 原生检查缺失**：`libtoolChecker.so` 不在内置源码中，2 项原生检测自动跳过（不会崩）。
3. **`DetectFragment` 目前是独立组件**：安全页直接复用 `DetectViewBinder`，没有走 Fragment 事务；
   `DetectFragment` 保留供其它页面挂载使用（因此它在 release 包里属于未被引用代码，靠 keep 规则保留）。
4. **整改建议是通用方向**：按命中类别给出处置方向（排除列表 / OverlayFS+SUSFS / PIF / Zygisk 侧 / 模块作用域），
   不针对单个 App 的强校验做适配。
