## 二、三条路到底有什么区别

这是 KernelPatch（因此也就是 APatch / FolkPatch）对内核模块的理解，不是我们自己发明的：

| 方式 | 位置 | 生效时机 | 重启后 | 能否卸载 | 需要什么 |
| --- | --- | --- | --- | --- | --- |
| **嵌入** embed | boot 镜像里，kptools 打包 | `pre-kernel-init`，比 `/init` 还早 | 仍在 | 要重新打包 boot | kptools + 已打补丁的 boot |
| **加载** load | 运行时进内核 | **立即生效** | **失效** | 不用管，重启就没 | superkey + supercall |
| **安装** install | `/data/adb/ap/kpm/<id>/` | 开机加载 | 仍在 | 随时可卸载 | 只要 ROOT |

对应到 APatch 的界面语言：**嵌入** 就是显示成「已嵌入」的那些，**安装** 就是模块列表里能开关的那些，**加载** 则是热加载，重启即失效。

## 三、「加载」是怎么实现的（重点）

这是三条路里唯一需要跟内核直接对话的。APatch / FolkPatch 的做法是发起 KernelPatch 的 **supercall**：

```
syscall(45, superkey, ver_and_cmd(SUPERCALL_KPM_LOAD), path, args, NULL)
```

其中（取自 FolkPatch `apd/src/supercall.rs`）：

```rust
const SUPERCALL_KPM_LOAD: c_long = 0x1020;
ver_and_cmd(cmd) = ((major<<16 | minor<<8 | patch) << 32) | (0x1158 << 16) | (cmd & 0xFFFF)
```

**难点一直是 superkey**——它只有 APatch 自己知道。但注意：当 boot 镜像是以**明文模式**打补丁时，superkey 就存在那个镜像里，而那个镜像我们本来就在解析（V8 里为了回填 ROOT 授权已经读了）。所以：

> **不需要问用户要 key，也不联网、不落盘。** 从用户自己的 boot 镜像里读出来，用完就只在内存里。

### 怎么发 syscall

没有 NDK、没有交叉链接器，所以自己造了个工具：

- `app/src/main/assets/kpload.arm64` —— 4377 字节的 **freestanding aarch64 静态 ELF**
- 纯手写汇编（`kpload.S`），只用 `svc #0`，不链接任何 libc
- 因为链接器不支持 aarch64，ELF 头是用脚本手工拼的（一个 `PT_LOAD`，R+X）
- 运行流程：读 argv → `syscall(45, ...)` → 把返回值按十进制打到 stdout → `exit_group(0)`
- 用 `qemu-aarch64-static` 实测过：参数不足返回 `-22`(EINVAL)，正常调用能发出 syscall 并正确回传返回值；`atol` 对 64 位大数（version<<32 那种）解析准确

调用方是 `KpmShell.loadKpm(path, superkey, kpVersion)`。

### 什么时候「加载」用不了，为什么不骗你

| 情况 | 原因 |
| --- | --- |
| 内核里没检测到 KernelPatch | 根本没人接收 supercall |
| 非 arm64 设备 | helper 是 aarch64 的 |
| boot 是 **root-key hash 模式** | 镜像里只存了 superkey 的 SHA256，明文 key 拿不到。**这是设计如此，任何第三方都做不到** |

第三种情况会在弹窗里直接说明白，并建议改用「嵌入」或「安装」——这两条路完全不依赖 superkey。环境栏也会提前显示「热加载：可用 / 不可用 — 原因」。

### 一个安全细节

`superkey` 只存在 Activity 的一个 `volatile String` 字段里：**不写日志、不进 SharedPreferences、不显示、不联网**。`runLoad()` 失败时复制出去的原因文本里也**不含** key（只包含错误码和说明）。
